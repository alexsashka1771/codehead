# Кандидат Clinic Demo: устройство этапа

24 ноября 2026 года. Автор попросил продолжить после worker-этапа и подтвердил заглушку без локальной модели. Основа — R02/R03/R06/R07/R09/R11; это описание реализации сессии 3 ROADMAP, нормативный источник остаётся TECHNICAL_SPEC.md.

## Результат и граница

Новый тестовый run проходит PM → Architect → CTO → параллельные Backend/Frontend. После решения автора инженеры возвращают отдельные файлы через тот же provider-интерфейс. Файлы принимаются с проверкой области и base_hash, сохраняются неизменно в PostgreSQL и материализуются в отдельной версии workspace. Происхождение заглушки явно: artifact origin=test, manifest origin=test_injected; технический каркас имеет origin=template. Тестовый кандидат не является доказательством генерации реальной LLM.

Основная фабрика сохраняет существующий дизайн и риги. Интерфейс показывает версию кандидата, профиль/хэши, происхождение и производителей файлов, родительскую версию и код. После сборки файлов очередь блокируется на ещё не подключённых QA/DevOps. Публичного preview и автоматического исполнения кода в origin платформы на этом этапе нет. Ручные доверенные проверки кандидата дают фактическую проверку HTTP и сборки, с отдельным отчётом.

Новые run закрепляют workflow clinic-v2, clinic_demo/v1, хэши профиля и внешнего suite. Старый clinic-v1 сохраняет прежнюю границу исполнения и историю. Настройки live не появляются; платные запросы и локальные модели исключены.

## Профиль и технический каркас

Доверенный каталог profiles/clinic_demo/v1 содержит profile.json, JSON-схемы HTTP, внешний acceptance/test_http.py, пустой технический template и отдельные versioned fixtures. Ни Backend, ни Frontend не могут писать в этот каталог. Профиль и проверки фиксируются до изготовления fixtures.

Контракт следует R02: UUID; врачи name/specialty, пациенты full_name, записи doctor_id/patient_id/starts_at/status; GET/POST/PATCH и атомарная отмена; 201/200/404/409/422 с code/message. PATCH меняет только переданные поля; пустой объект и неизвестные поля отвергаются 422. starts_at — строка RFC3339 с явным смещением, UTC в ответе, выровненные 30-минутные будущие слоты в Asia/Yekaterinburg. Создание/перенос защищены двумя частичными уникальными индексами scheduled. Перенос допускается только для активной будущей записи; отмена сохраняет историю и идемпотентна.

Template содержит backend/main.py, requirements.lock, frontend/index.html, src/main.tsx, package.json/package-lock.json, tsconfig и Vite config. Прикладных обработчиков и экранов в template нет. Проверенный кэш зависимостей берётся из подготовленной среды по profile+locks+Windows+Node/Python; неполный кэш имеет dependency_unavailable. Повторный dev не устанавливает пакеты.

Backend fixture: backend/clinic_api.py, clinic_storage.py, clinic_models.py. Frontend fixture: frontend/src/App.tsx, api.ts, styles.css. Frontend — компактный журнал приёмов с отдельными разделами врачей/пациентов, формами, отменой/переносом, загрузкой/пустыми состояниями и доступным объяснением 409. Только синтетические данные, часовой пояс виден. Интерфейс приложения имеет собственную спокойную типографику и зелёно-графитовую палитру; внешний дизайн фабрики сохраняется.

## Предложения и хранение

ProviderRequest получает только входные артефакты предков и descriptor основы файлов своей области. ProviderResult добавляет files: tuple[FileProposal, ...], отдельно от небольших документов. FileProposal содержит relative_path, base_hash|null, media_type, content. Один файл до 64 KiB, до четырёх файлов и 256 KiB в атомарном наборе. Только завершённый stop_reason=stop; дубликаты, невалидный UTF-8, несоответствие схемы/лимита/области не применяются.

Backend пишет backend/clinic_*.py из закреплённого набора, Frontend — frontend/src/App.tsx, api.ts, styles.css. Lockfiles, scripts, template entry points и профиль недоступны для записи. Пути нормализуются с учётом Windows: абсолютные/UNC/device, .., ADS, NUL, 8.3, reserved names, trailing spaces/dots и reparse-переходы отвергаются. Проверка выполняется до и после файловой записи; process_only не обещает защиту от намеренной гонки замены ссылок.

Сравнение base_hash и применение всего набора сериализованы блокировкой Run. Изменение другой области не инвалидирует независимое предложение. Несовпадение основы сохраняет failed attempt и блокирующее file_conflict-решение; retry_files создаёт следующую попытку с актуальной основой. Последний записавший не перезаписывает чужую версию.

Candidate хранит descriptor последнего manifest: id/run_id, revision, status, profile/suite/template hashes, files, manifest artifact_id и workspace revision. Каждый manifest и каждый файл — immutable artifact; новая версия указывает parent artifact/hash и producer attempt, точные входные версии. Нормализация — UTF-8 BOM removal + CRLF/CR→LF без удаления пробелов/финального LF; SHA-256 файлов и дерева по отсортированным путям.

## Worker, материализация и UI

CLI имеет два слота исполнения; каждый использует существующие короткие claim/begin/heartbeat/finish-транзакции. Лимит Run max_parallel_tasks остаётся 1–2. Провайдер и запись workspace выполняются вне транзакции и HTTP. Пауза/отмена/unknown исходы учитывают обе операции; fencing не позволяет позднему worker принять результат.

Материализация берёт только committed immutable manifest и verified content. Workspace .data/candidates/<candidate_id>/v<revision> принадлежит конкретной версии, manifest проверяется по фактическим байтам. Идемпотентный повтор сверяет существующие файлы, не перезаписывает изменённую версию и не удаляет каталоги. Ошибка материализации сохраняется как понятное состояние/причина; код не запускается от чтения snapshot или журнала.

Snapshot и workflow.updated добавляют candidate с совместимым значением null. Проекция проверяет run scope, сохраняет descriptor и время; property-проверка включает непустые source_code и manifest. API добавляет список артефактов run и чтение candidate descriptor. HTML показывает код как текст с nosniff, без выполнения HTML.
