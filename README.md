# CodeHead

Приватный репозиторий — [alexsashka1771/codehead](https://github.com/alexsashka1771/codehead). Правила веток, коммитов, проверок и авторства — [GIT_WORKFLOW](docs/GIT_WORKFLOW.md).

CodeHead — локальная фабрика разработки на Python/FastAPI, PostgreSQL и React/TypeScript с изометрической 3D-сценой. Проекты, задачи, проверки кандидата, доставка и сессии preview сохраняются в PostgreSQL.

Визуальная переработка: большая процедурная фабрика, семь разных роботов, графитовая ночная тема с голубыми и оранжевыми акцентами. Управление, карточка роли и данные раскрываются по запросу; подписи зон появляются при наведении или фокусе. Светлая тема доступна отдельно.

Worker исполняет тестовую цепочку PM → Architect → CTO, запрашивает решение автора и подключает Backend и Frontend в двух независимых слотах. Новый запуск закрепляет `clinic-v4`, профиль, внешний HTTP-набор и технический каркас. После публикации кандидата Runner проверяет Python, HTTP и сборку фронтенда. QA может открыть до двух итераций repair с новыми задачами Backend и QA.

«Запустить тест» использует помеченный тестовый провайдер. Прикладные файлы имеют происхождение `test_injected`, каркас — `template`. Сценарии `standard`, `repair_success` и `repair_blocked` показывают обычный кандидат, red → green и блокировку после двух неудачных исправлений. После успешного QA worker фиксирует ZIP с исходниками и проверенной сборкой, выполняет smoke на свежей SQLite и передаёт результаты DevOps для подготовки пакета и инструкции. История `clinic-v1/v2/v3` доступна в пределах соответствующего этапа. Live отключён.

## Запуск на Windows

Предпосылки: Windows x64, Node.js 24/npm 11, Python 3.11 и доступ к сети для первой установки. Docker и системная служба PostgreSQL не нужны.

В PowerShell из папки проекта:

~~~powershell
npm run setup
npm run dev
~~~

После готовности открыть [CodeHead](http://127.0.0.1:5180). API — [health](http://127.0.0.1:8010/health), PostgreSQL — 127.0.0.1:55432. Скрипт не останавливает чужое приложение, если порт занят.

setup устанавливает версии из package-lock.json и requirements.lock, создаёт .venv и браузер Chromium для проверок. Перед повторным setup завершите dev через Ctrl+C; скрипт отдельно корректно остановит свой PostgreSQL, чтобы Windows освободила DLL. Данные сохраняются. Повторный dev не устанавливает зависимости. Python-супервизор выполняет миграции, создаёт случайный токен команд в памяти и запускает API/UI/worker. Ctrl+C останавливает их собственное дерево; локальный PostgreSQL и данные остаются.

Для явной остановки локального кластера без удаления данных:

~~~powershell
npm run db -- stop
~~~

Данные — .data/postgres, база codehead. Только для этого локального учебного кластера применяется trust на loopback без пароля: доступные этому пользователю локальные процессы могут подключаться к нему. Для другого сервера передайте CODEHEAD_DATABASE_URL через окружение; не сохраняйте пароль в исходниках.

Имена переменных указаны в [.env.example](.env.example). Для прямого запуска API нужен CODEHEAD_COMMAND_TOKEN; при npm run dev его создаёт супервизор. Настройки провайдера, модели и token/cost бюджета потребуются перед этапом live. Ключи из сторонних конфигураций не используются.

## Что можно проверить в интерфейсе

1. Нажать «Новый проект» в верхней строке и создать Clinic Demo с учебным описанием.
2. Открыть «Управление проектом» первой кнопкой слева, выбрать тестовый сценарий и нажать «Запустить тест». Метка «ТЕСТ · заглушка» остаётся видимой; очередь содержит семь начальных задач с зависимостями, сначала исполняются три роли.
3. Обновить страницу: проект, очередь и журнал сохранятся; данные открываются нижними вкладками.
4. Выбрать роль через персонажа или нижнюю полосу; посмотреть попытку, версии входов, документы и редактированный trace. Во вкладке «Решения автора» принять либо отклонить архитектуру CTO. После принятия Backend/Frontend создадут кандидат; открыть исходный файл или manifest и проверить производителя/основу. CTO повторно не вызывается. История QA показывает проверенную ревизию, TestReport/Bug и цепочку repair; вкладка «Проверки» — полный вывод/exit code. «Не проверено» в карте требований не означает успех: сборка не доказывает работу UI/preview.
5. После успешного `clinic-v4` открыть вкладку «Preview». В ней доступны ZIP, отчёты QA и smoke, документ DevOps и инструкция. Нажать «Запустить preview» и дождаться готовности, затем нажать «Открыть». Clinic Demo работает в iframe на отдельном loopback-origin. Для остановки используется «Остановить preview». Учебные данные SQLite сохраняются для той же версии пакета.
6. Переключить день/ночь, приблизить фабрику или сбросить вид. При отсутствии сохранённой настройки используется ночь.
7. Через управление приостановить, продолжить или отменить запуск. После отмены можно создать новый и вернуться к предыдущему через историю.
8. Закрыть панель крестиком или Escape. Введённый текст формы сохраняется. Одновременно раскрыта одна панель. Escape сначала скрывает открытую подсказку.

Одновременно допускается один незавершённый run. Без WebGL доступны формы, роли, очередь, документы, решения и команды. Пауза/отмена ждут известного завершения текущей операции; unknown outcome сохраняет блокировку и путь подтверждения. Планируемые модули помечены в разделе «Возможности». CODEHEAD_TEST_STEP_DELAY_SECONDS задаёт наблюдаемую задержку заглушки (по умолчанию 1 секунда, до 5); она не имитирует Live.

## Проверки

~~~powershell
npm run test:backend
npm run check
npm run build
npm run test:e2e
npm run test:e2e -- --with-worker tests/e2e/runner.spec.ts tests/e2e/candidate.spec.ts tests/e2e/worker.spec.ts
npm run test:e2e -- --with-worker tests/e2e/quality.spec.ts
npm run test:e2e -- --with-worker tests/e2e/preview.spec.ts
npm run test:clinic
npm run test:runner
npm run test:qa
npm run test:preview
~~~

Backend использует отдельную codehead_test и новую schema test_<uuid> для каждого теста. E2E запускает отдельные API/UI на 8011/5181 с новой тестовой schema и останавливает их после проверки. Обычный прогон отключает worker для управляемого состояния; --with-worker запускает отдельный worker и ждёт его heartbeat. Пользовательская база codehead не очищается. Тестовые схемы/отчёты сохраняются; автоматического DROP/TRUNCATE нет.

E2E включает последовательности команд с проверкой snapshot == event projection, reload, восстановление WS при задержанном usage, защиту выбора от запоздавших списков/сохранения, выдвижные панели, сохранение ввода, видимость ошибок Start, подсказки/Escape, масштаб, day/night, отсутствие/потерю WebGL и размеры 1366/1920/430. Скриншоты/trace/HTML-report находятся в .data/reports/e2e-<timestamp>.

Результаты визуальной переработки — [UI_REDESIGN_REPORT](docs/UI_REDESIGN_REPORT.md), история foundation — [STAGE_01_REPORT](docs/STAGE_01_REPORT.md). Большой лениво загружаемый графический chunk пока остаётся предметом оптимизации; успешная сборка не означает измеренные 60 FPS.

`test:clinic` создаёт legacy clinic-v2 run через worker в отдельной тестовой schema, проверяет материализованную версию по frozen HTTP-suite на свежей SQLite, TypeScript, сборке и браузерным сценариям с управляемыми HTTP-ответами. Исходники и хэши проверяются повторно, отчёт сохраняется в .data/reports/clinic-candidate-<timestamp>. `test:runner` ставит три настоящие операции в сохраняемую очередь clinic-v2 и исполняет их через worker; отчёт — .data/reports/runner-<timestamp>. `test:qa` выполняет три clinic-v3 сценария, выделяя отдельную schema каждому; проверяет настоящие red/green, лимит repair, immutable историю и hashes. Выбор одного сценария: `npm run test:qa -- --scenario repair_success`. Отчёт — .data/reports/qa-<timestamp>.

`test:preview` прогоняет сценарии `clinic-v4` на настоящем Runner и проверяет ZIP, локальный health-check, явный старт, остановку и отказ при изменении пакета. `npm run test:preview -- --scenario repair_success` выбирает один сценарий. Отчёт сохраняется в `.data/reports/preview-<timestamp>`.

Уровень `process_only` рассчитан на проверяемый учебный кандидат. Runner ограничивает команды, окружение, время, вывод и собственное дерево процессов. Полная изоляция файлов и сети требует контейнерного или удалённого Runner. Лимиты составляют 180 секунд, 256 KiB на поток вывода, 16 MiB и 1024 файла для пакета. Неизвестный исход сохраняется в истории с состоянием `uncertain`.

Фактические результаты QA/repair — [QA_REPORT](docs/QA_REPORT.md), Runner — [RUNNER_REPORT](docs/RUNNER_REPORT.md), кандидата — [CLINIC_REPORT](docs/CLINIC_REPORT.md), история worker-этапа — [WORKER_REPORT](docs/WORKER_REPORT.md).
